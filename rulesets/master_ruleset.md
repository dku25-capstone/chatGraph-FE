## 1. 개발 프로세스 (Strict Workflow)

1. **이슈 단위 작업**: 모든 작업은 `issue.md`에 정의된 원자 단위 태스크로만 수행한다. 범위를 벗어난 오버 엔지니어링을 금지한다.
2. **명세 우선 참조**: 코드를 제안하기 전 반드시 `Engineering_PRD.md`, `tech_spec.md`, `api_spec.md`를 먼저 분석하고 이를 기반으로 답변한다.
3. **승인 프로세스**: 사용자의 명시적 승인(Accept) 없이는 다음 태스크로 넘어가지 않는다.

## 2. 주먹구구식 코딩 금지 (Anti-Hack Principles)

- **땜질 금지**: 질문이 길어져 맥락이 복잡해지더라도 설계도를 벗어나는 '임시 처방용 코드'를 제안하지 마라.
- **일관성 유지**: 기존 코드베이스와 아키텍처 패턴을 파괴하는 새로운 라이브러리나 패턴을 독단적으로 도입하지 마라.

## 3. 자가 검토 및 리뷰 (Self-Reviewer Mode)

- **비판적 검토**: 코드 작성이 끝나면 스스로 (`front_ruleset.md` 또는 `back_ruleset.md`)를 준수했는지 라인 바이 라인으로 검토한다.
- **거절 권한**: 만약 사용자의 요구사항이 기존 아키텍처를 해칠 경우, 이를 지적하고 대안을 제시하며 작업을 거절(Reject)하라.

## 4. 대화 체크포인트 및 리셋 (Context Management)

- **맥락 오염 방지**: 대화가 길어져 답변의 품질이 떨어진다고 판단되면 즉시 영민에게 "대화창을 새로 열거나 맥락을 리셋하자"고 먼저 요청하라.
- **리셋 명령 준수**: 사용자가 "체크포인트 리셋" 혹은 "명세 재로드"를 명령하면 즉시 이전 대화 내용을 배제하고 원본 문서들(`master_rules.md` 포함)을 기준으로 사고를 초기화한다.

## 5. 커밋 및 문서화 규칙

- 모든 커밋 메시지는 `git_rules.md` 형식을 엄격히 따른다.
- 작업 완료 후 필요 시 `git_rules.md` 내의 PR request 양식에 맞춰 작업 내용을 요약 보고한다.
- A이슈 내의 태스크 하나를 끝낼 때마다 스스로 여러 `ruleset`을 준수했는지 검토한다.
- **1 Task = 1 커밋**: `git_rules.md`에 맞춰 아주 작은 단위로 커밋을 한다.
